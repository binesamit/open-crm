# Security review — Bines OS

This document is the record of three security reviews of the Bines OS codebase, for contributors, self-hosters and
security researchers who want to know what was examined, what was found and how it was fixed. It is a historical
audit: each part describes the code as it was at the time (October 2026). Findings marked **fixed** were fixed in the
code, with a regression test where one is named; findings marked **open** were still open when this document was last
updated. Finding ids (S-01 …) are cited from source comments and tests, so they are stable.

Related audits: [`AI-SECURITY-REVIEW.md`](AI-SECURITY-REVIEW.md) (agents, MCP, AI columns),
[`EXTENSIONS-SECURITY-REVIEW.md`](EXTENSIONS-SECURITY-REVIEW.md) (extensions, outbound MCP) and
[`PERFORMANCE-REVIEW.md`](PERFORMANCE-REVIEW.md). To report a vulnerability, see [`SECURITY.md`](../SECURITY.md).

# Part 1 — full review

Scope: `apps/api`, `apps/web`, `apps/worker`, `packages/*`, the git history (145 commits at the time) and a staging
environment (passive scanning only). Production was not scanned.

## Summary

- **No critical finding.** No real secrets in git, no dangerous raw SQL; account isolation (`X-Account-Id` +
  membership), API tokens (hashed, scopes, board limits) and rich text (server-side allowlist) were sound.
- **Two high findings — fixed:**
  1. **SSRF in webhooks**: the server followed redirects (including to `169.254.169.254`, the cloud metadata
     service) and stored the target's answer in the delivery log; an address like `http://[::ffff:127.0.0.1]`
     bypassed the check; and DNS rebinding was possible (one lookup for the check, another for the connection). Now:
     no redirects are followed, the checked address is the address connected to, and the blocked IP ranges are
     complete.
  2. **Automation secrets were exposed to everyone who could see the board** (viewers and guests included): the
     inbound webhook secret, outbound webhook headers (for example another system's `Authorization: Bearer …`), the
     signing secret and Make / Zapier hook URLs. Now anyone who cannot edit the automation gets a redacted recipe.
- **Medium — fixed:** a guest could create automations and invite people on an "edit everything" board (contrary to
  [`05-PERMISSIONS.md`](05-PERMISSIONS.md) §2); the activity log showed values of view-restricted columns; there were
  no security headers (CSP, HSTS, X-Frame-Options, nosniff, Referrer-Policy); CSV export was open to formula
  injection.
- **Low — fixed:** uploaded HTML / SVG files opened inline; an open redirect through `?redirect=/\evil.com`; no cap
  on request body size.
- **Proposals S-10 – S-15 — implemented:** the real client IP behind a reverse proxy (by configuration, not by
  guessing), a mandatory inbound-webhook secret sent only in a header, a limit on invitation emails, an updated
  esbuild, no SVG for avatars / logos, and no disconnecting an admin of another account. Per-account (token) and
  per-IP rate limits were added as well ([`06-API.md`](06-API.md) §1.10).
- **CI**: `.github/workflows/security.yml` — `pnpm audit` (high and above, production dependencies), OSV (report),
  Semgrep (fails on ERROR), Gitleaks over the whole history (`.gitleaks.toml` with a narrow allowlist for one false
  positive), and a ZAP baseline against staging on demand.

## Checked and found sound

- **Account isolation**: every authenticated route goes through `requireAccount` (active membership, 404 for a
  foreign account, a token bound to its own account); repositories filter by `account_id`;
  `account-isolation.test.ts` passes.
- **Write permissions**: every service calls `loadBoardAccess` + `assertBoard` / `columnAllowed`; edit-restricted
  columns → 403; items hidden by `view_items` → 404; the admin console → 404 for anyone who is not the platform owner.
- **Guests (D23)**: only shareable boards they are subscribed to; no tokens, trash, activity, admin, workspaces /
  teams; SSE and export filtered (`guest-access`, `guest-isolation` pass) — and now no automations or invitations
  either (S-03).
- **API tokens**: only the SHA-256 is stored, shown once; scopes per path (default `admin`); board limits in
  `loadBoardAccess` and `readableBoardIds`; per-minute and per-day rate limits.
- **Files**: presigned PUT / GET (15 minutes), key `account/id/safeName` (no path traversal), size checked with HEAD,
  download only for the owner or someone who can see an item holding the file.
- **Rich text**: the server renders ProseMirror JSON through an allowlist, escapes all text, and allows only
  `http(s)` / `mailto` links; the link column accepts only `http(s)`.
- **Auth**: Better Auth — `httpOnly`, `SameSite=Lax` cookies, `Secure` in production; no open registration
  (invitation required) at the time; built-in rate limits (sign-in 3 per 10 s, magic link 5 per minute, password
  reset and email verification 3 per minute); `BETTER_AUTH_SECRET` of at least 32 characters required in production;
  invitation tokens hashed.
- **CORS**: only `WEB_ORIGIN` (a foreign origin gets no `Access-Control-Allow-Origin` — verified on staging).
- **SQL**: no raw SQL outside repositories; `sql.raw` only with constants (`query.repo.ts`).
- **Logs**: pino with redaction for authorization / cookie / password / token / secret; no logged tokens or magic
  links were found.

# Part 2 — delta review

Scope: everything added after the full review and not covered by [`AI-SECURITY-REVIEW.md`](AI-SECURITY-REVIEW.md)
(agents, MCP, AI columns, assistant) or [`EXTENSIONS-SECURITY-REVIEW.md`](EXTENSIONS-SECURITY-REVIEW.md)
(extensions, outbound MCP): dashboards and widgets, the document editor and its Hocuspocus WebSocket, platform
settings and email / SMS branding (including `GET /public/email-logo/{accountId}`), the API reference page
(`/api/docs`), token limits, column type conversion, dispatch listeners, maps and geocoding, bulk edit, import,
windowed loading, search, time reports, 2FA and IP allowlists. Method: code reading per area (authorization on every
route, IDOR, SSRF, XSS, CSRF / CORS on the WebSocket, rate limits, leaks), PGlite tests for every fix
(`apps/api/test/security-delta.test.ts`), and local automated scans. ZAP was **not** run (the staging build did not
match this code).

## Summary

- **No critical finding in our code.** A **dependency with a critical advisory** was found — `maplibre-gl` (maps): a
  bypass of its HTML sanitiser (XSS). The risk here is lower (only an account admin chooses the map style URL, and
  the CSP blocks scripts), but it was upgraded to the fixed version (6.12).
- **Medium — 9, all fixed:**
  1. **The live document editor** (WebSocket) did not check the account's IP allowlist or its mandatory 2FA, and a
     user who was deactivated or lowered to viewer while the document was open kept editing. Now: the same checks
     as the API, re-checked every 30 seconds; huge messages (up to 100 MB) are refused.
  2. **Google One Tap sign-in** (`/sign-in/social` with an idToken) skipped the 2FA code step.
  3. **The MCP server** did not check the account's IP allowlist — a leaked token worked from anywhere.
  4. **Search and the time report** showed item names from a private board through a "connect boards" column.
  5. **The time report** (on a board and on a dashboard) showed hours from a time column hidden from the user.
  6. **A dashboard** with many boards could freeze the server for everyone (quadratic computation).
  7. **An admin of one account** could inflate the CSP of every page in every account until pages failed to load.
  8. **The "copy from linked item" automation** read values from a private board / a hidden column its owner may not
     see.
  9. (The maps dependency — above.)
- **Low — 7 fixed:** a rate limit on Google place details (cost), SVG opened inline from a document export,
  compressed 6to4 addresses in the SSRF guard, a button template that read a hidden column, the dashboard live
  channel revealing when a private board changed, the per-account token budget not applying to MCP, and the tag
  length in secret encryption (a Semgrep ERROR).
- **Decided afterwards:** sender identity in email and SMS chosen per account (brand impersonation — S-46) and the
  full OpenAPI document being public (S-47) were both fixed. A few small metadata leaks remain open (see the table).

## Checked and found sound (delta)

- **Dashboards**: `loadDashboardAccess` filters by account, 404 for guests and board-limited tokens; edit / share /
  widgets with edit / manage checks; widget data goes through `readableBoardIds` (a token's `boardLimit` included) →
  `queryItems` (`item.read`, `view_items`, visible columns); widget text is rendered as text (no
  `dangerouslySetInnerHTML`), buttons use `noopener`.
- **Documents**: every route uses `requireAccount` + `loadDocAccess` / `assertDoc`; IDOR on versions / comments /
  threads filtered by account and document; collab token — HMAC, 5 minutes, bound to user / account / document;
  **CSWSH blocked** — `Origin` must be `WEB_ORIGIN` or the host; Hocuspocus ignores updates from a read-only
  connection; HTML export from an allowlist with CSP `default-src 'none'`, markdown escaped, printing in a sandboxed
  iframe; `markdown.ts` does not render raw HTML.
- **Platform settings**: owner only (404 for others), tokens blocked, no secrets in the response.
  **`/public/email-logo/{accountId}` is not an open redirect**: the target is always a presigned URL of an image asset
  of the same account (raster, ≤ 2 MB, not SVG), set only through `PUT /accounts/me/email-logo`; a suspended / deleted
  account → 404.
- **`/api/docs`**: CSP `script-src 'self'`, no inline script; config as JSON with `<` escaped; titles and description
  escaped; Scalar's AI disabled, `persistAuth=false`; the public document filters platform / extension / session-only
  routes.
- **SSRF**: every outbound call (webhooks, the webhook action, extensions, manifests, lifecycle, MCP, OAuth clients)
  goes through the guarded `rawRequest`; `attach_file_from_url` checks every redirect, the size and the MIME type;
  geocoding and SMS providers come only from the environment.
- **Column conversion / bulk edit / import**: board owner or admin only, `column.update` / `boards:write`, backup +
  restore; `restrictedEdit` is enforced in `writeCell`; xlsx is parsed on the client; no `eval` / `new Function`.
- **Export**: every CSV goes through `toCsv` + `csvSafeText`; xlsx uses `inlineStr` only (no formulas).
- **2FA / IP / tokens**: attempts limited, a trust-device cookie with HMAC, disabling 2FA blocked when the account
  requires it; saving an IP allowlist cannot lock out the person saving; tokens cannot manage tokens; a token's
  `board_ids` ⊆ what its creator can see.

# How to run the scans again

```
docker run --rm -v "$PWD:/src:ro" ghcr.io/google/osv-scanner:latest scan source --lockfile /src/pnpm-lock.yaml
pnpm audit --prod
docker run --rm -v "$PWD:/src:ro" -w /src semgrep/semgrep semgrep scan --metrics=off --config p/default --config p/typescript \
  --config p/nodejs --config p/secrets --config p/owasp-top-ten --exclude node_modules --exclude dist apps packages
docker run --rm -v "$PWD:/repo:ro" zricethezav/gitleaks:v8.30.1 git /repo --redact --config /repo/.gitleaks.toml
docker run --rm -v "$PWD/zap:/zap/wrk:rw" ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
  -t https://staging.example.com -r zap.html -J zap.json -I     # a staging environment only, passive
pnpm --filter @bines/api test security          # includes security-delta.test.ts (S-24 onwards)
```

In a git worktree (where `.git` is a file) Gitleaks / Semgrep cannot find the repository inside Docker — run
`gitleaks dir` on the tree, and `gitleaks git` on the main checkout (mounted read-only). An alternative without a
mount: `git log -p --all > history.patch`, then
`docker run --rm --network none -v "$PWD:/w" zricethezav/gitleaks:v8.30.1 dir /w/history.patch --redact --max-target-megabytes 200`
(map each finding to its commit / file by the `commit` / `+++ b/` lines above it).

In CI: `.github/workflows/security.yml` (push / PR); ZAP — `workflow_dispatch` with `zap: true`.
